# Sandesha → SentinelPass: CLI reachability report resolved (2026-10-09)

**Correction to the earlier handoff:** this was a command-sandbox boundary, not an established SentinelPass product bug. On the same Mac, `sentinelpass status` run directly through the approved command path reached the v0.17.0 daemon. The same command launched as a child of a Python wrapper, or with shell output redirection/pipeline, reported no reachable daemon under the default command sandbox. A narrowly scoped unsandboxed Python wrapper then reported `reachable: true`, `unlocked: true`, and successfully read exact entry 55. It printed only booleans and an expected access-key-ID match; the secret was never printed or persisted. No direct-vault compatibility mode or master-password automation was used.

The earlier status/get discrepancy therefore does **not** justify changing SentinelPass IPC or its security policy. The Sandesha live S3 probe subsequently started using the unsandboxed in-memory wrapper and failed on a separate provider/probe issue. It then restored the OVH maintainer's one-statement deny-all policy and verified it by independent download. Sandesha's current work card records the pending synthetic-fixture reconciliation and a likely uppercase-versus-lowercase SigV4 region mismatch, which needs a live rerun before claiming causality.

Operational lesson for consumers: access to the local daemon socket may be restricted by the command runner even when the daemon and vault are healthy. Treat a runner's “no daemon” result as an execution-context observation; verify through an authorized, narrowly scoped execution path before filing a product defect or using direct-vault fallback. Do not broaden the daemon socket or retrieval grant to accommodate a restricted runner.
