# macOS passkey provider feasibility

Status: ready for an isolated platform spike. Platform qualification and custody design are pending. This workcard follows the [Identity handoff](../handoffs/2026-11-20-identity-passkey-provider.md) and [passkey product design](../PASSKEY_PRODUCT_DESIGN.md).

## Starting point

- The [iOS extension](../../ios/SentinelPass/SentinelPassCredential/Info.plist) returns password credentials and shares the app vault group. Its project sources have no passkey callbacks or `ProvidesPasskeys` declaration. The macOS [Tauri configuration](../../sentinelpass-ui/tauri.conf.json) uses ad hoc signing and provides no native provider target. Treat iOS code as a UI reference only.
- Apple's AutoFill provider API supplies registration and assertion callbacks. Inspection of the macOS 26.5 SDK headers found the interactive request and completion APIs annotated for macOS 14.0 and later. This sets an API floor. The qualified OS floor will depend on signing, installation and observed browser behavior. Apple requires the AutoFill credential provider entitlement on the app and extension, and `ProvidesPasskeys` on both for registration. Check the distribution channel against Apple's capability matrix and verify the signed artifacts. [Provider class](https://developer.apple.com/documentation/authenticationservices/ascredentialproviderviewcontroller/) · [Registration callback](https://developer.apple.com/documentation/authenticationservices/ascredentialproviderviewcontroller/prepareinterface%28forpasskeyregistration%3A%29) · [macOS capabilities](https://developer.apple.com/help/account/reference/supported-capabilities-macos)
- Chrome documents the system credential path on macOS, including user permission. Chromium source carries a third-party provider name from the macOS API. Neither establishes registration and assertion routing for a particular SentinelPass build. Check Chrome and Safari independently. The browser's arbitrary-RP entitlement belongs to the browser path. The SentinelPass extension uses the AutoFill provider capability. [Chrome system path](https://developer.chrome.com/blog/passkeys-on-icloud-keychain/) · [Chromium provider metadata](https://chromium.googlesource.com/chromium/src/%2B/HEAD/device/fido/discoverable_credential_metadata.h) · [Apple browser entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.web-browser.public-key-credential)

## Route and signing spike

1. Use a separate macOS app and extension bundle identity and a dedicated test account. Use an available Apple team and verify the signed app and nested extension entitlements. Record Xcode and SDK versions, macOS build, browser build, distribution class, app build digest, and whether the system offers and enables the provider. Keep signing identities and account details in local custody.
2. Enable the provider through system settings. With a disposable HTTPS relying party (RP), request explicit registration and interactive assertion in Safari and then Chrome. The probe records only callback kind and a result enum. Cancel the callback using the system API. No credential material is needed to prove the browser can select the extension and deliver registration. Assertion routing with an actual provider-owned key is a later test. To distinguish routes, record the system/provider label and compare with the platform authenticator baseline. A browser success alone does not attribute a ceremony to SentinelPass.
3. Record each browser independently as `registration_callback_observed`, `assertion_callback_observed`, `provider_unavailable`, or `not_run`. Capture the reason when configuration, permission, signing, or routing fails. An unavailable browser keeps its support row closed. A successful Safari route permits architecture review for Safari while the Chrome requirement remains open.

## Custody decision before usable enrollment

Review a separate typed passkey store with scoped signing as a device-bound first slice. Select the key authority, supported algorithms and attestation policy after platform and RP compatibility tests. Bind each signing operation to the exact RP, credential, authenticated extension request and fresh system-backed user authorization. Keep origin, challenge and type validation in the browser/RP trust chain. The provider receives the system request and binds its operations to the supplied RP and client-data hash. It cannot reconstruct a verified origin from that hash. Define behavior for vault lock, provider disable, account removal, device loss, interrupted registration and duplicate registration before wiring the store. Private key material stays out of generic entry APIs, browser messaging, text exports, metadata references and logs. Sync, export, recovery and passkey replacement need separate design review. [WebAuthn ceremonies and authenticator data](https://www.w3.org/TR/webauthn-3/)

## Acceptance for a real provider build

| Check | Pass condition |
| --- | --- |
| Registration | User selects SentinelPass in the system flow and the disposable RP accepts a fresh provider-created public credential. Repeating the ceremony follows the reviewed replacement policy. |
| Assertion | After browser sign-out and provider restart, the RP checks a fresh assertion from the same SentinelPass credential. Test both directed and discoverable sign-in where the browser supports them. |
| Authorization | Verify platform-mediated approval. Confirm physical Touch ID with the human on a dedicated run. The WebAuthn UV flag proves authenticator-reported verification and does not identify the user verification method. |
| Binding | Run denial cases for a different RP, mismatched credential, stale/replayed challenge, wrong origin, and cancellation. Confirm the relevant boundary refuses the request with no successful authentication. |
| Lifecycle | Test locked and disabled provider, interrupted save, restart, deliberate removal, and separate deletion of a metadata reference. Verify each outcome in provider and RP state. |
| Identity | On the disposable dev account, enroll, sign in, approve an exact reversible owner action and verify return to the initiating workspace. Keep this evidence separate from the existing platform-passkey run. |

Record only build versions, provider attributed by the UI and confirmed callback, verification outcome, and sanitized test status. Retain no keys, challenges, credential identifiers, user handles or biometric details. Update the security status matrix only for browser and lifecycle rows actually demonstrated and independently reviewed.
